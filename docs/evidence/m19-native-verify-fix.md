## Fixed defects (this run)

### 1. Conflict prompt invisible while owning input (S5)

Native reproduction on the pre-fix binary proved the chain:

- Dirty buffer + external disk change + `Ctrl+S` produced only the passive
  notice `Save: file changed on disk since it was opened`.
- The async disk check completed and `ExternalDecision` reached
  `AwaitingDecision`, so `computed_input_owner()` returned `Confirmation`
  (verified via temporary `eprintln` gates, since removed).
- The prompt element was painted (log-proven) but invisible: it used absolute
  positioning while the opaque editor surface paints after it, burying it.
- With the owner stuck at `Confirmation` and the `r`/`o`/`Escape` handling
  living only in `on_editor_key` (unreachable without editor ownership),
  every key was swallowed with no reachable resolution except invisible
  prompt buttons — a full input wedge requiring no further input to persist.

Fix (`87bc5bf`): the prompt renders in-flow like every other banner, and
`on_key_down` resolves `Reload (r)` / `Overwrite (o)` / `Cancel (Esc)` while
a dirty external decision is up.

Verified on the fixed binary with on-disk byte assertions:

| Case | Result |
|---|---|
| Dirty conflict → prompt visible (screenshot `probe-verify2.png`) → `o` | PASS, disk == buffer (`DIRTY1plain text`) |
| Dirty conflict → `r` | PASS, buffer == disk, clean (`RELOADDISK`) |
| Dirty conflict → `Esc` | PASS, prompt dismissed, dirty retained, disk untouched (`DISKEXT2`) |
| Clean buffer + external change → prompt `Changed on disk. Reload…` (screenshot `probe-shutdown2.png`) → `r` | PASS, buffer == disk |
| Typing works before and after every resolution | PASS (`VERIFY2`, `AFTERFIX` landed) |
| Terminal input after `Ctrl+1` (`echo …` executed, clean prompt) | PASS |

### 2. Reopened paths forked buffers → invalid snapshot (S4)

The restart probe relaunched into a registry written by the pre-fix binary and
hit snapshot recovery: `duplicate document descriptor`. Root cause: the store
deduped by opened-file device/inode only, so reopening a path after an
external atomic replacement (new inode) forked a second live buffer; the
exporter then emitted two descriptors for one `(project, root, path)` key.

Fix (`b28ca8a`): frozen dedup key `(ProjectId, RootIdentity, normalized
path bytes)` checked first, inode map kept for contained-alias convergence;
restore commit checks both; the exporter can no longer emit a duplicate path
key. Three new unit tests
(`reopen_after_external_replacement_converges_without_forking`,
`contained_alias_and_dotdot_spellings_converge_on_one_buffer`,
`save_updates_file_key_and_reopen_still_converges`).

Verified: post-fix snapshots validate with zero duplicate keys, and the
relaunch below restored without any recovery banner.

## Harness finding: singleton displacement

All previously observed "spontaneous instance deaths" are explained: launching
a second desktop on an occupied runtime dir silently displaces the running one
(it exits with no log line). Reproduced 5/5 times, always immediately after
my own relaunch-into-occupied-dir. Not an app crash (no coredump, no panic
log). Rule for all future native runs: kill-before-relaunch **and** verify
death first; never share a runtime dir between instances.
